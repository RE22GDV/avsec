## 1. Криптографічний профіль

| Параметр | Значення |
| --- | --- |
| Основний AEAD | ChaCha20-Poly1305, [RFC 8439](https://www.rfc-editor.org/rfc/rfc8439) |
| Альтернативний AEAD | AES-256-GCM (лише для окремого порівняння) |
| Довжина тега | 16 байтів, **повний**, ніколи не скорочується |
| Ключ сеансу | 32 байти |
| Nonce | 12 байтів |
| Виведення ключів | HKDF-SHA256 |
| Ідентифікатор сеансу | 8 випадкових байтів з `os.urandom` |
| Епоха сеансу | 32 біти, автентифікована і врахована у виведенні ключа |

Примітиви беруться з бібліотеки `cryptography`. У цьому репозиторії **не**
реалізовано самостійно ані ChaCha20, ані Poly1305, ані AES, ані HKDF.

### Виведення ключів

```
okm = HKDF-SHA256(
        ikm  = master_secret,       // 32 байти, попередньо спільний секрет
        salt = session_id,          // 8 випадкових байтів
        info = "avsec/v2" | direction | stream_id | algorithm | epoch(4 Б BE)
               | "key+nonceprefix",
        L    = 36)
key          = okm[0:32]
nonce_prefix = okm[32:36]
```

Розділювач полів `info` — байт `|`. Два напрями, два потоки **або дві епохи**
ніколи не мають спільного ключа.

### Nonce і його неповторюваність

```
nonce = nonce_prefix (4 Б) || counter (8 Б, big-endian)
```

`counter` строго монотонний усередині **однієї епохи**. Два шифрування
збігаються за nonce лише якщо збігаються і ключ, і лічильник.

**Виділення лічильника одноразове.** У API немає способу задати або повторити
номер: `Sealer.seal(plaintext, aad)` виділяє лічильник сам, а `aad` можна подати
функцією `counter -> bytes`, щоб заголовок, якому потрібен власний номер,
будувався **всередині** виділення. Номер списується до побудови AAD і до
шифрування, тому виняток у будь-якому з цих кроків не повертає його в обіг.

Межа лічильника `2^64 − 1` обробляється явною помилкою `NonceExhausted`, а не
переповненням.

### Поведінка після перезапуску

Після перезапуску передавач зобов'язаний зробити одне з двох:

1. згенерувати **новий** `session_id` (свіжі ключі, епоха 0); або
2. лишити той самий `session_id` і **підняти епоху** —
   `SessionState.begin_epoch()`, який зберігає нову епоху **до** першого
   відправлення. Оскільки епоха входить у виведення ключа, новий ключ робить
   безпечним початок лічильника з нуля.

Відновлення **тієї самої** епохи дозволене лише над збереженим запасом
лічильників: `Sealer` резервує діапазон у стійкому сховищі **до** використання
(`reserve_chunk` + `persist`, атомарний запис через `os.replace`), а
`SessionState.restore()` відмовляється, якщо запасу немає, бо аварія між
шифруванням і записом стану інакше призвела б до повторення номерів.

### Лабораторні та робочі ключі

`lab_master_secret(seed)` — **єдиний** детермінований шлях; він позначає ключ
`origin="lab"`, і ця позначка подорожує разом з об'єктом до звітів. Seed
бенчмарку не може непомітно керувати робочими ключами: робочий режим —
`generate_master_secret()` або `load_master_secret(path|env)`.
Ключі не зберігаються в репозиторії, логах і звітах; `repr` майстер-секрету
друкує `<32 bytes redacted>`.

## 2. Канонічний бінарний заголовок

Порядок байтів — **big-endian**. Розмір ядра 52 байти, плюс 4 байти CRC-32.

| Зсув | Байтів | Поле | Значення |
| ---: | ---: | --- | --- |
| 0 | 2 | `magic` | `A5 53` |
| 2 | 1 | `version` | версія протоколу (2) |
| 3 | 1 | `profile_id` | транспортний/кодековий профіль |
| 4 | 8 | `session_id` | ідентифікатор сеансу |
| 12 | 4 | `session_epoch` | монотонна епоха сеансу (**нове у v2**) |
| 16 | 1 | `stream_id` | логічний потік у сеансі |
| 17 | 1 | `codec_id` | 0 raw, 1 dct, 2 jpeg, 255 filler |
| 18 | 4 | `frame_id` | номер кадру джерела |
| 22 | 2 | `stripe_id` | номер смуги в кадрі |
| 24 | 1 | `desc_id` | номер опису в смузі |
| 25 | 1 | `seg_id` | номер сегмента в описі |
| 26 | 1 | `n_segs` | кількість сегментів опису |
| 27 | 1 | `n_descs` | кількість описів смуги |
| 28 | 8 | `unit_seq` | лічильник AEAD == номер для захисту від повторів |
| 36 | 2 | `x0` | геометрія: ліва колонка в кадрі |
| 38 | 2 | `y0` | геометрія: верхній рядок у кадрі |
| 40 | 2 | `width` | кількість **відліків** по горизонталі |
| 42 | 2 | `height` | кількість **відліків** по вертикалі |
| 44 | 1 | `step_x` | крок підрешітки по x |
| 45 | 1 | `step_y` | крок підрешітки по y |
| 46 | 1 | `phase_x` | фаза підрешітки по x |
| 47 | 1 | `phase_y` | фаза підрешітки по y |
| 48 | 2 | `payload_len` | довжина ciphertext без тега |
| 50 | 1 | `flags` | біт0 останній сегмент, біт1 смуга завершена, біт2 filler |
| 51 | 1 | `reserved` | має бути 0 |
| 52 | 4 | `header_crc32` | CRC-32 байтів `[0:52]` |

Байти `[0:52]` подаються **дослівно** як associated data AEAD, тому кожне поле
криптографічно прив'язане до вмісту. Заголовок v1 (48-байтне ядро без епохи)
відхиляється статусом `unknown_version`.

Однозначність з'єднання полів забезпечена фіксованою довжиною кожного поля:
жодне значення не може бути прочитане як інша комбінація полів (перевірено
тестом `test_header_field_concatenation_is_unambiguous`).

### Геометрія

Одиниця покриває пікселі кадру
`(y0 + phase_y + j·step_y, x0 + phase_x + i·step_x)`
для `0 ≤ j < height`, `0 ≤ i < width`.

### CRC і довіра

CRC-32 — транспортний засіб, щоб **знайти і попередньо прочитати** заголовок до
автентифікації. Він **ніколи** не замінює тег. Заголовок, який успішно
розібрано, лишається **недовіреним**, доки не пройде перевірка тега; усі поля,
використані до перевірки, проходять жорсткі перевірки меж
(`payload_len ∈ (0, max]`, `1 ≤ step ≤ 16`, `phase < step`, `seg_id < n_segs`,
`desc_id < n_descs`, геометрія в межах кадру, `reserved == 0`).

## 3. Транспортна одиниця

Профіль v2 використовує **фіксовані розміри одиниць і фіксований розклад**:

```
plaintext  = payload || нулі до unit_plain_bytes        (реальна довжина у payload_len)
ciphertext = AEAD_seal(key, nonce(counter), plaintext, aad = header[0:52])
wire       = RS_header(header 56 Б) || RS_payload(ciphertext || tag)
```

Оскільки довжина plaintext стала, усі одиниці мають однаковий розмір у каналі,
а розклад повністю детермінований і публічний.

### Що лишається видимим

* структура синхронізації растру і пілотні комірки (фіксований публічний шаблон);
* межі одиниць і розклад слотів (фіксовані, публічні);
* поля заголовка: версія, профіль, ідентифікатор сеансу, **епоха**, потік, номери кадру,
  смуги, опису, сегмента, геометрія, довжина корисних даних, прапорці;
* загальний обсяг трафіку і його часова структура — **стала** за конструкцією,
  доки увімкнено передавання одиниць-заповнювачів (`send_filler`).

Режим змінних довжин у цьому профілі не використовується. Якщо його вмикати,
потрібне окреме застереження про витік довжин.

### Слот і автентифікація — важлива властивість

**Фізичний слот, у якому подорожує одиниця, не автентифікований.**
Автентифікована **семантична позиція**: сеанс, епоха, потік, кадр, смуга, опис,
сегмент, геометрія. Наслідок, зафіксований тестом
`test_slot_order_is_not_authenticated_but_position_in_the_picture_is`:

* перестановка двох одиниць між слотами **нешкідлива** — кожна одиниця сама
  каже, куди належить, і зображення збирається правильно;
* підміна координат одиниці (інша смуга, інший кадр, інший опис) **не проходить**
  перевірку тега.

Слот впливає лише на розміщення в растрі (а отже на стійкість до пакетних
пошкоджень), а не на коректність зображення.

## 4. Захист від помилок

| Блок | Код | Призначення |
| --- | --- | --- |
| Заголовок | RS(52+`nsym_h`, 52) над GF(256) | знайти і прочитати заголовок |
| Корисні дані | RS(`k`+`nsym`, `k`) над GF(256), блоками | відновити ciphertext і тег |

Правило блокування: повідомлення довжиною `L` ділиться на `ceil(L/k)` блоків;
усі блоки, крім останнього, несуть рівно `k` байтів, останній — **скорочений**.
Закодована довжина `L + nblocks·nsym`, тому обидві сторони обчислюють розкладку
з самої лише `L`.

Порядок операцій на передавачі:
незалежне джерельне кодування → AEAD → FEC для ciphertext разом із тегом →
перемежування → відображення у сигнал. На приймачі — обернений.

Стирання приймач визначає **сам**, з власних спостережень: символ, що відстоїть
від найближчого рівня більше ніж на `erasure_threshold · крок рівнів`,
позначається ненадійним. Істинну маску помилок симулятор не передає.

Зміна, яку FEC повністю виправив до початкового захищеного повідомлення, **не**
вважається успішною підробкою; невідновні зміни тестуються окремо
(`run_protocol_checks`).

## 5. Правила приймача

Приймач:

* не передає неперевірений plaintext у декодер зображення;
* не вважає правильний CRC заміною автентифікації;
* не приймає повторно вже прийняту одиницю;
* **оновлює стан захисту від повторів лише після успішної автентифікації** —
  підроблений пакет із великим номером не може заблокувати справжні дані;
* має обмеження на довжини, виділення пам'яті (`MAX_PAYLOAD_LEN`), кількість
  одночасних сеансів (`max_sessions`) і строк актуальності (`max_frame_age`);
* відкидає невідомі версії та профілі визначеним способом.

Структуровані статуси замість `None`:

`verified`, `filler`, `idle`, `header_unrecoverable`, `header_invalid`,
`unknown_version`, `unknown_profile`, `payload_unrecoverable`, `auth_failed`,
`replay`, `stale`, `stale_epoch`, `session_closed`, `decode_failed`, `no_sync`,
`session_limit`.

Втрата ключового контексту, синхронізації або місткості каналу **не** запускає
автоматичне передавання відкритого зображення: захищений режим повідомляє про
недоступність даних, а незахищені базові методи запускаються тільки явно.

Автентифікованими є отримані **кодовані дані**. Пікселі, домальовані
інтерполяцією на їх основі, не є криптографічно підтвердженими вимірюваннями
камери і завжди позначені в карті доступності.

## 6. Кеш ключів і реєстр сеансів — це два різні об'єкти

Раніше це був один обмежений LRU-кеш `Opener`-ів, який виконував дві незв'язані
роботи: тримав **виведені ключі** (щоб не запускати HKDF удруге) і тримав
**вікно захисту від повторів разом із позначкою свіжості кадру** — тобто єдине,
через що записаний раніше растр відхиляється.

Змішування робить політику витіснення кеша рішенням про безпеку. За
`max_sessions = 4` будь-що, що змусить приймач побачити чотири інші контексти
сеансу, витісняє справжній; разом із ним зникає вікно повторів, і раніше
записаний растр автентифікується знову, бо приймач більше не пам'ятає, що ці
номери вже використовувались (дефект **R01**).

Тепер це два об'єкти (`avsec.receiver.sessions`):

| | `KeyCache` | `SessionLedger` |
| --- | --- | --- |
| Що тримає | `SessionKeys` (матеріал HKDF) | допустимість, вікно повторів, позначку свіжості |
| Що коштує витіснення | одне виведення HKDF | **нічого не витісняється: сеанс ЗАКРИВАЄТЬСЯ** |
| Чи впливає на рішення | ні | так, це і є рішення |

### Життєвий цикл контексту `(session_id, epoch, stream_id)`

`UNKNOWN → ACTIVE`
: лише коли одиниця з цим контекстом **автентифікувалася**. Допуск відмовляється
  наперед, якщо контекст уже `CLOSED` або його епоха відкликана.
  `SessionLedger.classify()` лише читає, тож підроблений чи пошкоджений
  заголовок не може просунути контекст цим шляхом.

`ACTIVE → CLOSED` (остаточно)
: за трьох подій, кожна з яких потребує автентифікованої одиниці:
  1. активною стала строго вища епоха того самого `(session_id, stream_id)`;
  2. активна таблиця заповнена, і цей контекст — найдавніше автентифікований:
     його **витісняє** новіший сеанс;
  3. застосунок закрив сеанс явно.

  `CLOSED` — остаточно. Закритий контекст відхиляється зі статусом
  `session_closed` стільки, скільки реєстр його пам'ятає.

### Поведінка після перезапуску приймача

Свіжість — це стан, а процес, який стартує без стану, не може відрізнити живий
сеанс від його запису. Тому політика названа явно, а не мається на увазі:

* **`tofu`** (за замовчуванням) — довіра при першому використанні, окремо для
  кожного контексту. Невідомий контекст допускається, і його перша
  автентифікована одиниця встановлює позначку. Це коректно лише якщо передавач
  після кожного перезапуску приймача починає новий `session_id` або піднімає
  `session_epoch` — що `Transmitter.new_session()` і `new_epoch()` роблять.
* **`persisted`** — реєстр відновлено з файла (`import_state`) до першого
  растру, тож контексти, закриті до перезапуску, лишаються закритими, а позначки
  свіжості переживають рестарт.

Режим повертає `SessionLedger.describe()`, тож жоден звіт не може навести
результат про повтори, не назвавши, у якому режимі він отриманий.

### Обмеженість памʼяті, названа прямо

Реєстр точно памʼятає `retired_capacity` закритих контекстів. Ідентифікатор
сеансу — 8 випадкових байтів, тож необмежений потік справжніх сеансів не може
бути запамʼятований точно в обмеженій памʼяті **ніким**; коли запис витісняється,
лічильник `forgotten_closures` зростає, і `describe()` про це повідомляє. Для
будь-якої кількості сеансів у межах ємності — а це все, що виконує цей
репозиторій, — памʼять точна.

### Що лишилося без змін

Стан приймача **не змінюється до автентифікації**, і це властивість інтерфейсу:
`classify()` лише читає, невідомий контекст отримує свіже вікно повторів, яке
встановлюється лише в `commit()`, а той викликається **після** успішного
`open()`. Без цього правила N+1 неавтентичних заголовків із різними
`session_id` витісняли справжній сеанс (дефект F01).

## 7. Свіжість за автентифікованим контекстом

Найновіший номер кадру ведеться для кожного `(session_id, epoch, stream_id)`
окремо, а найвища прийнята епоха — для кожного `(session_id, stream_id)`.
Наслідки:

* кадр №0 нового узгодженого сеансу або нової епохи приймається після кадру №10
  попереднього;
* одиниця завершеної епохи відхиляється статусом `stale_epoch`;
* підроблений номер епохи або кадру нічого не блокує, бо жоден водяний знак не
  рухається до автентифікації.

## 8. Правила приймача B3 (AEAD цілого кадру)

Приймальна сторона `B3Receiver` не отримує від передавача **нічого**. З
прийнятих заголовків вона відновлює:

| Величина | Звідки |
| --- | --- |
| кількість фрагментів | `n_segs` |
| довжина ciphertext | `payload_len + 16` |
| лічильник AEAD | `unit_seq` |
| канонічний AAD кадру | той самий заголовок із `seg_id = 0` |

Кожне поле обмежується до використання (`payload_len + tag ≤ n_segs · frag_size`,
геометрія має збігатися з профілем кадру), а фрагменти групуються лише за
полями, які потім будуть автентифіковані. Окремі відновлені FEC-фрагменти **не**
вважаються автентифікованими, доки не пройде перевірка тега цілого кадру.
