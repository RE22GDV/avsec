# Протокол експериментів і розділення даних

## 1. Три профілі запуску

| Профіль | Конфігурація | Мета |
| --- | --- | --- |
| `smoke` | `configs/smoke.yaml` | швидка перевірка працездатності |
| `comparison` | `configs/comparison.yaml` | відтворюване порівняння B0–B4 і P |
| `research` | `configs/research.yaml` | розширений прогін із багатьма реалізаціями каналу |

Додатково: `configs/attack.yaml`, `configs/cvbs.yaml`, `configs/tuning.yaml`.

**`smoke` не є доказом новизни чи реалістичної якості зв'язку.**

## 2. Спільність умов

Порівняння вважається чесним лише тоді, коли для всіх методів однакові:

* початкові дані та базовий строк відображення;
* доступний час (растрів на кадр) і допустимі рівні сигналу (амплітудне вікно);
* обмеження смуги (геометрія растру і частота);
* спосіб задання шуму і пакетних пошкоджень (той самий `RasterChannelConfig` і
  ті самі seed-и реалізацій каналу);
* порівнянний ресурс добору параметрів.

Це закріплено в `SharedBudget`. Метод, який не вміщується в бюджет, **виключається
з явною причиною**, а не отримує більше растрів. Різна потужність або пік-фактор
неможливі: амплітудне вікно `[level_low, level_high]` спільне, і аналоговий
носій `AnalogCarrier` використовує рівно те саме вікно, що й цифровий модем.

Порядок модуляції та розмір комірки символу лишаються вільними параметрами, бо
вони змінюють **спосіб** використання бюджету, а не його обсяг.

## 3. Розділення даних

`split_sources` ділить **цілі послідовності** (ніколи не кадри однієї
послідовності) на три частини:

| Частина | Частка | Використання |
| --- | --- | --- |
| калібрувальна | 0,4 | добір параметрів (`Tuner.search`) |
| валідаційна | 0,3 | вибір серед фіналістів |
| тестова | 0,3 | **лише після фіксації конфігурації** |

`Tuner.score(..., split="test")` кидає `RuntimeError`. Витік тестових даних у
добір неможливий через інтерфейс, а не лише за домовленістю.

## 4. Статистика

* Агрегування — на рівні **незалежних послідовностей/сеансів**. Сусідні кадри
  одного відео не вважаються незалежними повтореннями.
* Для кожної метрики звітується середнє і 95% довірчий інтервал
  (нормальне наближення, `mean_ci95`).
* Для порівнянь методів рахуються **парні** різниці за спільними
  послідовностями (`paired_difference`) з позначкою значущості.
* Кількість незалежних реалізацій каналу задається `channel_realisations`.

## 5. Що зберігається з кожним прогоном

* повна розв'язана конфігурація (`resolved_config.yaml`, поле `config` у JSON);
* версії залежностей і характеристики платформи (`environment`);
* hash вмісту кожного джерела (`inputs`, `content_sha256`);
* seed відтворюваної **несекретної** частини експерименту;
* ідентифікатор конфігурації;
* git commit, якщо репозиторій git реально існує (інакше `null`, без вигадування);
* кількість успішних, невдалих і пропущених випробувань (`counters`);
* сирі результати: `frames.csv`, `frames.jsonl`, `summary.csv`.

**Секретні ключі звичайних сеансів у ці записи не входять.** У профілях
експериментів `key_mode: lab`, і це видно у звіті.

## 6. Обов'язкові метрики

| Група | Що вимірюється |
| --- | --- |
| Якість | PSNR, SSIM, приклади реконструкції на однакових вхідних даних |
| Повнота | частка отриманих і перевірених одиниць, частка кадру з актуальними даними |
| Час | обчислення по етапах, накопичення, модельна наскрізна затримка, вік даних |
| Канал | корисна швидкість, повна зайнятість, символьні помилки до і після FEC |
| Відновлення | час повторної синхронізації, кількість втрачених одиниць |
| Цілісність | відкинуті зміни та повтори, причини відмов |
| Ресурси | wall-clock час етапів, кількість растрів, залежність від розміру кадру |

### Правило двох поглядів на якість

Якість завжди рахується **двічі**:

1. для **повного відображеного зображення**, з визначеним способом заповнення
   втрат;
2. для **доступних актуальних ділянок** разом із часткою їхнього покриття.

Це не дозволяє методу отримати високий PSNR, просто відкинувши складні ділянки:
`psnr_verified` без `coverage` не має сенсу і ніколи не наводиться окремо.

### Знаменники для SER

Правильний початковий потік символів доступний **лише оцінювачу**. Знаменник
(`symbol_error_denominator`) — це число символів у **реально зайнятих** слотах;
він звітується разом із помилкою, щоб відкидання всього потоку не давало
штучно «ідеальний» показник.

## 7. Розділення висновків

У звіті кожне твердження позначене:

| Позначка | Означає |
| --- | --- |
| `[ЗАПУСК]` | підтверджений результат фактичного запуску в цьому репозиторії |
| `[МОДЕЛЬ]` | висновок, що діє лише в межах моделі симуляції |
| `[ІНЖЕНЕРНЕ ПРИПУЩЕННЯ]` | наше проєктне рішення |
| `[ГІПОТЕЗА]` | дослідницька гіпотеза, ще не встановлена |
| `[НЕ ВИКОНАНО]` | перевірка, яку не було проведено |

Окремо розділяються: якість після джерельного кодування без каналу; додаткове
погіршення через канал; наслідки криптографічної перевірки та відкидання;
користь перемежування і кількох описів.

## 8. Абляції

Порівнюються з `P`:

* один опис;
* послідовне розміщення;
* звичайне блочне перемежування (мала і велика глибина);
* запропоноване розміщення;
* кілька розмірів AEAD-одиниці;
* кілька рівнів FEC;
* мілке вікно BAWP.

**Криптографічна міцність і довжина тега зафіксовані** (16 байтів) у всіх
варіантах: зменшення захисту ніколи не використовується як спосіб показати
виграш швидкодії. Режими без FEC або без AEAD допустимі лише як діагностика і
позначені `secure=False`.

Якщо виграш отримано тільки завдяки додатковій надлишковості, нижчій якості
джерельного кодування або більшій затримці — саме так і формулюється висновок.

## 9. Оцінка вартості прогону

Перед довгим пошуком друкується оцінка (`Tuner.estimate_cost`): кількість
кандидатів, кадрів на кандидата й очікуваний час. Необмежений перебір не
запускається; великі набори даних не завантажуються без потреби.

## 10. Відтворення

```bash
PYTHONPATH=src python -m avsec.cli benchmark --config configs/comparison.yaml --output runs/benchmark
PYTHONPATH=src python -m avsec.cli report --input runs/benchmark --output reports/benchmark
```

Несекретна частина повністю відтворювана за `seed`; ключі сеансів — ні (і не
повинні бути).
